## Confirmed issues and launch risks

### Block launch: no committed source baseline or remote

The current application `.git` has branch `main` but no commits, and `git status` reports the application files as untracked. No remote is configured. There is no immutable reviewed revision to tie to test evidence, release archives, or a production rollback. This also makes it easy to build or ship unintended workspace files.

**Fix:** establish the approved repository and remote, review and commit the intended source, tag a release commit, build from that clean revision in a controlled pipeline, and retain the source revision and artifact SHA-256 with each deployment record. Confirm generated release packages exactly match that commit.

### Medium: no automated test and release gate is checked into the project

The application root contains no GitHub Actions, GitLab CI, Azure Pipelines, Jenkins, or other checked-in CI configuration. `README.md` documents a manual backend `unittest` command, and the Android README documents test/lint/build commands, but no project automation binds those checks to a reviewed commit or deployment package. A maintainer can therefore change backend, Android, or release-builder code and create a deployable ZIP without a repeatable gate proving the required suites, lint, APK identity/signing checks, and package validation were run on that exact source. The current checkout also has no commit baseline, so no existing automation result can be tied to a release revision.

**Fix:** establish a controlled CI/release workflow after creating the source baseline. On every reviewed change, install from the approved dependency lock and run backend tests, Android unit tests/lint, and clean release-package validation. For release tags, build Android and backend artifacts from the tagged clean commit, verify signatures and manifests, publish checksums/provenance, and retain results with the artifacts. Keep company VM, Entra, and physical tablet acceptance as separate human deployment gates.

### Medium: the documented backend test command omits three checked-in test modules

`README.md` instructs developers to run `python -m unittest -q development.tests.test_app`, which only discovers the tests in `test_app.py`. The repository also contains `test_email_notifications.py` (9 `test_` methods), `test_microsoft365_setup.py` (4), and `test_kiosk_flow_contract.py` (9); none is imported by the documented command. The internal handoff separately names the kiosk-flow module but does not give a command for the two email suites, so there is no single documented command that runs all checked-in Python tests. A developer following the README's backend command can get a passing result while skipping 22 checked-in backend/email/visitor-flow tests. This is a static test-source count; no suite was executed in this review.

**Fix:** document one command that discovers all Python test modules, such as `python -m unittest discover -s development/tests -p "test_*.py"`, and make the release gate use that same command with all declared test dependencies installed. Add a guard that ensures new test modules are included in the canonical command and record conditional skips explicitly.

### Medium if a Debian deployment package can be replaced in transit or staging: the installer does not authenticate the package

`tools/linux/install_debian.sh` checks only that `.env.example` and `app/RELEASE_MANIFEST.txt` exist before installing. `tools/build_release.py` creates that manifest as descriptive text; it contains no package digest or signature, and the installer does not parse or verify it. The documented flow extracts the ZIP and runs the installer, with no independent artifact checksum/signature verification step. If someone can replace the ZIP or extracted tree in the transfer/staging location, the root installer will copy and execute the substituted application code. No evidence establishes that the deployment channel is compromised; this is a conditional supply-chain integrity gap.

**Fix:** sign the release archive or a provenance statement with a key kept outside the package, and verify that signature and approved source revision before extraction and again before installation. If signatures are not operationally available, require a SHA-256 value delivered through a separately controlled channel and compare it before extraction; do not treat a manifest inside the same archive as independent verification. Add installer acceptance for altered, missing, and mismatched artifacts.

### High: pilot sign-off can pass without identifying the software release or disposing of known launch risks

`docs/COMPANY_PILOT_RUNBOOK.md` records pass/fail for HTTPS/networking, the backend service, email, backup/restore, tablet acceptance, and one fictional end-to-end visit. It does not capture the backend source revision, deployment ZIP checksum, APK version/checksum/signer, test/lint/package-validation evidence, or the disposition of open launch-blocking/high-severity findings. The runbook says not to use real visitor data until the pilot is approved and required checks pass, but its sign-off criteria do not make software provenance or unresolved-risk approval a required check. A pilot could therefore be approved against an untraceable or different build while known high-impact issues remain open.

**Fix:** extend the sign-off record with the reviewed source commit, backend ZIP and APK hashes, APK package/version/signer, test/lint/build/package-verification results, and links to the completed physical and server acceptance evidence. Require each launch-blocking or high-severity finding to be fixed or explicitly risk-accepted by a named company owner before approval to use real visitor data; preserve the approval with the deployment record.

The Android Gradle build only assigns the `release` signing config when a local `keystore.properties` file exists. That ignored file exists in this checkout, but I did not open its credential/path contents and cannot establish that it references the approved production key or is under company custody. ### Low if the Android deployment output path is mistyped: the ZIP builder can overwrite its input APK

`build_android_deployment.ps1` resolves the APK input and normalizes `OutputPath`, but does not compare them. It copies the APK to a staging folder, builds the ZIP, then runs `Move-Item -Force` to the requested output path. If `-OutputPath` names the same file as `-ApkPath`, the successful command replaces the source APK with the ZIP; a path collision with another important file can likewise overwrite it. This is a conditional operator-error/data-loss risk.

**Fix:** canonicalize both paths and refuse when the output resolves to the APK input or another protected source/package input. Keep intentional replacement of the prior deployment ZIP supported, but write to a temporary file in the destination directory and replace it only after validation. Add a PowerShell test proving an APK/output collision fails and leaves the APK checksum unchanged.

### High if a debug tablet can handle real visitor data: debug mode permits cleartext kiosk traffic

`KioskSettings` sets `allowInsecureHttp` whenever `ApplicationInfo.FLAG_DEBUGGABLE` is present, `KioskUrlPolicy.validServerUrl()` then accepts an `http://.../kiosk` URL, and the debug `network_security_config.xml` sets `cleartextTrafficPermitted="true"`. The WebView origin policy will accept that configured HTTP origin, so an operator can provision the debug APK against a non-TLS backend and submit visitor names, company/contact details, and photographs over the local network in cleartext. The source provisioning guide explicitly directs operators to install the debug APK, and the repository does not enforce synthetic-only use of that installed debug app.

**Fix:** require HTTPS for every device build that can reach a real backend, including debug builds used for physical acceptance. If insecure HTTP is needed for isolated automated tests, confine it to a separate non-deployable test variant and loopback-only test harness; do not include that variant in provisioning artifacts. Add a release and device-configuration check proving the provisioned tablet cannot select or load an HTTP origin.

### High if the company HTTPS endpoint uses a private CA: the production app does not trust that CA unless it is in Android's system store

The production `network_security_config.xml` disables cleartext but declares no company trust anchor, and `SECURITY_MODEL.md` confirms that the app uses Android system trust only. The APK targets Android 14/API 34; Android documents that apps targeting API 24 or later do not trust user-added CAs by default, and a managed certificate installed in the user trust store therefore does not make the kiosk WebView trust a private company CA. The Debian deployment guide correctly says that such a CA needs a reviewed app-specific trust configuration, but no approved root certificate or domain-scoped release configuration is present in this workspace. If IT chooses that TLS topology without updating and rebuilding the APK, managed URL validation and page loading will reject the kiosk server and check-in cannot start. Publicly trusted certificates remain compatible with the current system-only trust model. [Android Network Security Configuration](https://developer.android.com/privacy-and-security/security-config).

**Fix:** prefer a publicly trusted certificate for the approved internal hostname when the company DNS/certificate process supports it. If a private CA is required, obtain its approved public root, add it only to a `domain-config` for the exact kiosk hostname (including an explicit policy for subdomains), and ship that change in the reviewed production APK; do not enable all user-installed CAs app-wide. Test certificate-chain, hostname/IP SAN, renewal/rotation, and rejected-untrusted-root behavior on the exact managed Android build before provisioning.

### Low to medium if visitor archives grow large: scheduled backups repeatedly read complete archives in the shared background worker

### Low if two backups are created during a daylight-saving clock rollback: filename sorting can misidentify and prune the newest archive

### Medium if Windows backups or photo operations exceed ten seconds: storage-lock contention aborts work

The Linux `flock` path does not have this fixed ten-attempt cutoff. No Windows contention test was found in the current test suite. [Python `msvcrt.locking`](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking).

**Fix:** replace the Windows lock acquisition with a documented wait policy that cannot silently give up before supported backup work completes, or use an explicit deadline and return a distinct retryable service error before mutating state. Bound and monitor the maximum lock hold time, keep backup work under the same consistency boundary, and cover a held lock longer than ten seconds in Windows process-level acceptance.

### Medium if Debian backup snapshots take a long time: blocking storage locks can stall visitor writes

A large photo library or slower/cross-filesystem storage can therefore leave request threads waiting for the full snapshot duration; the Apache proxy timeout is 60 seconds, so visitors or administrators can receive a failed request while the backend remains blocked and may later complete the operation. This is distinct from the Windows lock's fixed ten-second exception, and no POSIX contention test was found.

**Fix:** set a bounded, observable lock-wait policy on POSIX and return a controlled retryable response before starting a write when the deadline expires. Reduce the critical section while preserving a consistent database/photo snapshot, and size the proxy timeout to the documented operation bounds. Add Linux process-level contention coverage that exceeds the wait limit and confirms request threads recover without ambiguous commits or unbounded accumulation.

Add a generated-package check that extracts every local link and confirms its target exists and remains inside the package.

### Medium if build inputs contain a symlink: the release builder can copy content from outside its allowlisted source files

`_copy_file()` checks `source.is_file()` and then calls `shutil.copy2()`, both of which follow a source symlink by default. `_write_operator_guide()` likewise reads each allowlisted document path without rejecting symlinks or confirming canonical containment under `source_root`. The package validator checks destination names, PEM private-key markers, the developer path, and populated sensitive keys in `.env.example`, but it does not scan the other staged files for credentials. A symlink substituted for an allowlisted document or runtime input can therefore pull out-of-tree content into the company ZIP; likewise, a credential accidentally committed into an ordinary allowlisted code or operator document would not be caught by the current checks. The archive could then contain secrets despite the destination allowlist and manifest claiming that secrets are excluded. No symlink or known real credential was identified in the reviewed release inputs; this is a future/build-input risk.

**Fix:** for every copied and concatenated source input, reject symlinks and non-regular files, resolve the canonical path, and require it to remain beneath the canonical source root before reading. Add a secret-scanning gate over the staged package that checks common credential formats and known project secret names, with narrowly documented false-positive exceptions. Add a package-builder test that points an allowlisted input outside a temporary source tree and verifies the build refuses it before creating the archive, plus a test that confirms a synthetic credential in a regular allowlisted file blocks packaging.

### Medium: a lost response or visitor retry can create duplicate check-ins and email

`static/kiosk.js` prevents a second submit from the same live page while its request is pending, but `POST /api/checkins` has no idempotency key or duplicate suppression. If the server commits the photo and record but the response is lost, the page reports failure and lets the visitor retry; that retry creates a second row/photo and can send another host email. There is no server-side transaction key tying retries to the original result.

**Fix:** issue a one-time submission identifier when a check-in begins and persist it with a uniqueness constraint and the final response; repeated requests with the same identifier should return the original outcome without creating a second record or sending a duplicate message. Add failure-after-commit and retry coverage and make the visitor UI explain whether a retry is safe.

### Low if an employee is deactivated during a check-in: a stale active lookup can still create a new visit

`create_checkin()` calls `Database.get_employee()` and accepts the returned active employee before decoding the submitted photo, then writes the photo and later calls `create_visit()` with the earlier employee snapshot. `Database.create_visit()` inserts the row by employee ID without checking that the employee is still active. If an administrator deactivates the selected employee during that interval, the already-started request still creates a visit and queues an alert for that employee. The gap includes filesystem writes and can be noticeable for a large/slow photo; no concurrency acceptance test covers this ordering.

**Fix:** make the final active-employee check and visit insert one SQLite transaction, using the current employee row's name and ID only when `active = 1`. If the employee was deactivated before that transaction, reject the check-in and clean up the staged/final photo; if the visit commits first, treat the later deactivation as applying only to future check-ins. Add a synchronized concurrency test for both orderings.

### Medium if the network can stall: a check-in submission can remain pending indefinitely

`submitCheckin()` calls `fetch("/api/checkins", ...)` without an `AbortController` or request deadline. Until the promise settles, it keeps `submitting` true, disables the photo action, displays “Submitting…”, and has already cancelled the abandonment timer. The `offline` handler may show an overlay, but its retry button only reloads employees and does not cancel or resolve the check-in request. On a connection that silently stalls instead of promptly rejecting, the visitor can be left in this state indefinitely and their name, details, and photo remain on screen. `loadEmployees()` also has no request deadline; its retry timer is scheduled only after a fetch or response-processing error, so a stalled initial host-list request never reaches that recovery path. A client timeout would still leave check-in commit status ambiguous, so blindly resubmitting could create the duplicate record described above.

**Fix:** give both check-in and employee-list requests bounded client deadlines and restore a usable, privacy-bounded state when they expire. For check-ins, show clear “status unknown” wording; preserve the submission idempotency key across timeout/retry so an already-committed request returns its original result, and never treat client abort as proof that the server did not save the visit. Keep employee-list retry bounded and visible. Add coverage for a fetch that never settles, offline/online changes during submission, a server commit followed by a stalled response, host-list timeout/retry, and expiry of the personal-data cleanup deadline.

### Medium if Microsoft identity or Graph is slow: email delivery blocks the visitor's check-in response

After saving the photo and visitor row, `create_checkin()` calls `deliver_notification()` synchronously and does not send the success response until token acquisition and the initial email attempt return. The Graph `urlopen()` call has a 15-second timeout, but the MSAL token-acquisition calls on this path are not given an explicit timeout here. A slow identity or mail service can therefore leave the visitor waiting after the check-in is already committed and hold a request thread while a public kiosk is in use. This compounds the browser's missing deadline and can prompt a retry of an already-saved visit.

**Fix:** finish the check-in response after the durable visit/photo commit and send all notifications through a durable background queue. Give identity and Graph operations explicit bounded timeouts, expose the persisted `pending`/`sent`/`failed` state to the admin, and tell the visitor that the record was saved while notification is pending. Keep the idempotency key so a lost response or retry cannot create another visit. Add coverage proving a stalled identity/Graph provider does not hold the visitor response open and that queued alerts remain recoverable.

### Low: offline banner promises automatic retry that is not implemented for check-ins

`static/kiosk.js` displays “We will keep trying automatically” on the browser `offline` event, but the `online` handler only updates connection status and reloads the employee list. A failed check-in request returns to photo review and requires a manual submit; there is no queued or automatic check-in retry. This can leave visitors unsure whether their record was sent, and encouraging an uncertain manual retry intersects with the duplicate-check-in risk above.

**Fix:** change the status text to describe the actual behavior, or implement a clearly bounded retry flow using the same persisted idempotency key. Add browser contract coverage for offline during submission, server commit with lost response, and reconnection.

### Medium: failed check-in submissions disable the abandoned-visitor cleanup timer

`submitCheckin()` clears the 90-second abandonment timer before sending the visitor record. If the request fails, times out, or its response cannot be parsed, the catch path returns to photo review with the visitor's entered details and captured photo still on screen, but it does not call `armAbandonmentTimer()` again. If the visitor walks away after a failed attempt, the next person can see the previous visitor's personal details and photo indefinitely until another manual action or app reload.

**Fix:** re-arm a bounded abandonment timer on every failed submission while preserving the data for an immediate retry, and reset the form/photo when that timer expires. Show the remaining recovery window clearly, and test rejected fetch, non-JSON/error response, and server-commit/response-loss cases without removing the separate idempotent-retry requirement.

### Medium: check-in abuse can exhaust storage or server capacity if network restrictions fail

Visitor submission is intentionally unauthenticated, each request can carry a multi-megabyte photo, and the threaded HTTP server has no per-client check-in rate/connection cap. The Apache example restricts this route to a tablet address, but it is only a template and the company network policy is not verified. If that restriction is omitted or misconfigured, automated requests can fill photo/database/backup storage or consume backend threads.

**Fix:** enforce and verify the tablet-only network boundary in Apache and the firewall; add bounded per-client submission/concurrency limits and operational alerts for request volume and storage growth. Retain a documented assisted/manual check-in procedure for outages.

### Medium if reachable by untrusted clients: slow request trickles can occupy unbounded backend threads

`KioskHandler.setup()` applies a 15-second socket-operation timeout, while `create_server()` uses `ThreadingHTTPServer`, which starts a thread for each accepted request and has no application concurrency limit. A socket inactivity timeout is not a total header/body deadline: a client that sends another byte before each blocking read expires can keep an incomplete request and its handler thread alive. The packaged Apache vhost does not set `RequestReadTimeout`, and the Debian installer/documentation do not explicitly enable `mod_reqtimeout`; whether a system default is active therefore depends on the host. The direct-TLS Windows path can also be exposed to the configured LocalSubnet firewall scope. Enough slow connections can consume backend threads and file descriptors even without submitting visitor data. [Python socket timeout semantics](https://docs.python.org/3/library/socket.html#socket.socket.settimeout), [Python `ThreadingHTTPServer`](https://docs.python.org/3/library/http.server.html#http.server.ThreadingHTTPServer), [Apache `mod_reqtimeout`](https://httpd.apache.org/docs/2.4/mod/mod_reqtimeout.html).

**Fix:** configure and verify bounded TLS-handshake, header, and body read deadlines at the Apache edge; also enforce an absolute request deadline and bounded concurrent connections at the backend, especially for direct-TLS/Windows deployments. Keep the service network-restricted. Add slow-trickle coverage that sends bytes just inside the inactivity timeout and confirms the request is closed within the absolute deadline without unbounded thread growth.

### Low if the unauthenticated check-in endpoint is reachable: deeply nested JSON escapes request validation as an uncaught exception

`read_json()` limits request bodies to 7 MB and catches `UnicodeDecodeError` and `JSONDecodeError`, but Python's JSON decoder can also raise `RecursionError` for deeply nested input. The public check-in route passes the decoded object to this parser before its field validation, and `handle_request_body_errors()` catches only `RequestBodyError`. A small nested payload can therefore bypass the normal JSON 400 response, close the request with a server-side exception traceback, and produce noisy repeated errors if the endpoint is reachable by untrusted clients. Python's documentation warns that untrusted JSON can consume substantial CPU/memory; CPython has documented this decoder `RecursionError` case. [Python JSON security note](https://docs.python.org/3/library/json.html), [CPython JSON decoder issue](https://github.com/python/cpython/issues/135835).

**Fix:** impose an explicit JSON nesting limit before or during parsing, and translate decoder `RecursionError` into a sanitized 400 response without catching unrelated programming errors. Add a request test with deeply nested arrays and objects below the body-size limit, asserting a bounded response and no uncaught handler exception.

### Low if unauthenticated request routes are reachable: overlong decimal Content-Length values escape validation

`read_json()` and `read_urlencoded_form()` call `int(length_header)` after confirming only that the header contains decimal characters; the request-size limit is checked after conversion. CPython 3.11 and later limit decimal integer-string conversions to 4,300 digits by default and raise `ValueError` when that limit is exceeded. An HTTP header containing more decimal digits than the limit can fit within the server's accepted header-line size, pass `isdecimal()`, and raise before either parser can translate the input into a `RequestBodyError`. The request handler's body-error decorator does not catch this `ValueError`, so a public check-in or OAuth callback request closes with an uncaught handler exception instead of a bounded 400/413. Existing length tests cover non-decimal text and a numeric value just over the body cap, but not an overlong decimal string. [Python integer-string conversion limit](https://docs.python.org/3.11/library/stdtypes.html#integer-string-conversion-length-limitation).

**Fix:** reject a Content-Length string whose digit count exceeds the maximum decimal width needed for the route's configured body cap before calling `int()`. Also translate conversion failures into a sanitized `RequestBodyError` as a defensive boundary. Add raw HTTP tests with an overlong decimal Content-Length for both JSON and OAuth form parsing and assert a bounded response with no uncaught exception.

### Low to medium: the Apache HTTPS template does not send HSTS

The supplied Apache vhost terminates TLS but does not add a `Strict-Transport-Security` response header, and it provides no HTTP-to-HTTPS redirect vhost. The Debian install procedure enables Apache but does not disable the packaged `000-default` site or require an explicit port-80 firewall block; if that default site remains enabled and port 80 is reachable, an HTTP request may receive the generic Debian site instead of a redirect. Browser clients therefore do not learn to require HTTPS after an initial secure visit, and operators may see a misleading HTTP endpoint. The Android client rejects HTTP, but administrator browser access still benefits from downgrade protection.

**Fix:** once the company hostname and trusted certificate are stable, add an HSTS header on the HTTPS vhost with a reviewed `max-age`. Explicitly disable the default port-80 site and block that port at the firewall, or provide a tested HTTP-to-HTTPS redirect vhost if the company intends to serve port 80. Avoid `includeSubDomains` until IT confirms its impact on every subdomain. Add acceptance coverage that checks the effective enabled sites and verifies that no kiosk endpoint or misleading default page is served over HTTP.

### Low if the backend is reachable by untrusted clients: the `Server` header exposes software versions

`KioskHandler` sets `server_version = "EliteRFKiosk/0.1"` but does not override `BaseHTTPRequestHandler.version_string()`. Python's standard library builds the default server version string from both `server_version` and `sys_version`, which includes the Python runtime version. Direct backend responses can therefore reveal the kiosk and Python versions to clients that can reach the listener, giving scanners more precise information for selecting implementation-specific probes. The Debian backend is intended to be loopback-only behind Apache; exposure depends on the selected host and proxy behavior. [Python `http.server` documentation](https://docs.python.org/3/library/http.server.html#http.server.BaseHTTPRequestHandler.version_string).

**Fix:** return a generic version string that excludes framework/runtime versions, or omit the `Server` header where the chosen server/proxy supports that. Verify both direct-backend and public-proxy responses in deployment acceptance; do not treat header hiding as a substitute for patching and network isolation.

### Medium if managed configuration is used: invalid managed kiosk URL silently falls back to a saved URL

`ManagedKioskConfiguration.selectedUrl()` returns the previously stored URL whenever the managed `kiosk_url` value is invalid. `MainActivity` then continues loading that saved origin without showing that the latest MDM configuration was rejected. If IT changes the endpoint but publishes a malformed value, the tablet can continue sending visitor information to an old server that still has a trusted certificate and passes the app's URL checks.

**Fix:** distinguish an absent managed value from a present-but-invalid one. Fail closed with a clear device status when a configured managed URL is invalid, and only use the locally saved value when no managed value is supplied. Add startup and live restrictions-change coverage for invalid, cleared, and valid managed URLs.

### Low if Android cannot persist kiosk preferences: server URL changes are reported successful before disk persistence is known

After the administrator's server URL passes the network/certificate probe, `validateAndSaveUrl()` calls `KioskSettings.setUrl()` and immediately reports “Server verified. Reloading kiosk.” `setUrl()` uses `SharedPreferences.Editor.apply()`, which changes the in-memory value immediately but writes asynchronously and provides no failure result. If the preference write fails, the running activity can use the verified new URL from memory while a later process/device restart loads the previous URL; the operator was told the change succeeded and receives no persistence-failure signal. No preference-write failure test was found. Android documents the asynchronous, unreported failure behavior of `apply()`. [Android `SharedPreferences.Editor.apply()` reference](https://developer.android.com/reference/android/content/SharedPreferences.Editor#apply())

**Fix:** persist a manual URL change with a checked synchronous `commit()` on a background thread before reporting success or switching the kiosk, and leave the current configuration in place with a clear error if persistence fails. Add a test that injects a failed write and verifies the UI does not claim success or load a URL that will be lost on restart; confirm successful changes after process recreation on the tablet.

### Low to medium if an MDM URL update coincides with activity resume: the new URL may be saved without reloading the WebView

`MainActivity.onResume()` calls `settings.applyManagedConfiguration()` but ignores its `true` result. The restrictions broadcast handler reloads the WebView only when that same call reports a change. If the restriction value becomes visible before its broadcast is handled and the activity resumes first, `onResume()` can persist the new URL without reloading; when the broadcast later arrives, it sees no further change and also skips the reload. The live kiosk can continue submitting visitor information to the previous trusted server until another reload or activity recreation.

**Fix:** route both resume and broadcast handling through one function that reloads the kiosk whenever the managed URL actually changes while the kiosk is fully locked, and clears the prior visitor session before switching origins. Add an activity-level test for the new-value-before-broadcast ordering and verify that requests after the change target only the new origin.

### Low: Android kiosk URL filtering accepts a path that serves the admin login shell

`KioskUrlPolicy.allowedPath` allows any path beginning `/static/` and compares other paths without first resolving `.` and `..` segments. `/static/../admin.html` therefore passes the policy's current source-level check. If the WebView sends that path unchanged, the backend's `/static/` handler takes `Path(path).name` and serves `static/admin.html`, exposing the admin login shell inside the kiosk. The shorter `/static/../admin` path does not serve that shell, because it resolves to a nonexistent `static/admin` file. The WebView may canonicalize the URL before the policy or server sees it; no test or device evidence in this review establishes the actual behavior. This does not bypass the separate admin API authentication, but it violates the kiosk's admin-route boundary and depends on browser normalization for safety.

**Fix:** canonicalize and reject dot segments, encoded separators, backslashes, and ambiguous path forms before applying the allowlist; match complete approved route patterns. Add URL-policy and WebView integration cases for `/static/../admin.html` and encoded variants, confirming the admin shell cannot render in the kiosk even if the server receives an unnormalized request.

### Medium if a saved or managed kiosk URL carries `#camera-calibration`: a visitor can persist native camera changes

`KioskUrlPolicy.validServerUrl()` checks the scheme, host, port, and path `/kiosk`, but does not reject a query or fragment. When an initial/manual or managed URL contains `#camera-calibration`, `MainActivity.loadConfiguredKiosk()` preserves it; `static/kiosk.js` sees that hash on page load, opens the camera-calibration step, and calls the JavaScript bridge's `NativeCameraController.start(..., calibration=true)`. The native controller shows its calibration controls and the “Save and Lock” action persists the transform with no fresh PIN or native authorization check. A visitor facing a kiosk configured with that fragment can therefore change the camera transform used for subsequent visitor photos, potentially making them rotated, mirrored, cropped, stretched, or zoomed until an administrator repairs calibration. No evidence shows that a production URL currently contains this fragment, and the documented supported URL is a bare `/kiosk` path. Separately, `#camera-debug` shows the development diagnostic panel in a release build because the web page checks only `location.hash`; native debug capture/write methods do check `isDebugBuild()`, so their artifact-writing path is blocked in release. The admin diagnostic panel displays the complete saved URL, so a sensitive query value would also be retained in preferences and shown to administrators.

**Fix:** reject queries and fragments during manual, initial, and managed URL validation, and clear any legacy fragment before loading. Enforce calibration authorization natively: `start(calibration=true)` and calibration persistence must require a short-lived grant created only after successful PIN verification, rather than trusting a URL hash or JavaScript argument. Gate the debug panel on an explicit debug-build capability and keep debug artifact methods disabled in release. Add tests for saved/MDM fragments and direct JavaScript bridge calls proving that neither calibration controls nor persistent calibration changes are available without fresh authorization; verify approved camera diagnostics still work in debug builds.

### Low if an operator or MDM supplies an out-of-range port: Android URL validation accepts ports that cannot be used

`KioskUrlPolicy.validServerUrl()` rejects port 80 but otherwise accepts any `URI.port` value, including `0` and values above the TCP port maximum. The initial setup path stores a URL after this syntax check without probing it, and `ManagedKioskConfiguration.selectedUrl()` also accepts it as valid and replaces the previously working endpoint. The kiosk then attempts to load/probe that URL and remains in its reconnect/error flow because the port cannot be opened. The authenticated URL-change screen does probe before saving, so this path specifically affects initial setup and managed configuration with a typo or malformed deployment value.

**Fix:** require an explicit port to be in the supported range 1–65535 (and keep any scheme-specific exclusions deliberate) before a URL can be persisted or accepted from MDM. Make initial setup verify reachability before finalizing setup, or clearly preserve an accessible recovery path. Add policy cases for port 0, 65536, the maximum valid port, and values that fail URI parsing, plus managed-config coverage proving invalid candidates do not replace the working URL.

### Low to medium: Android reachability probes can follow and accept redirects blocked by the WebView

`MainActivity.serverReachable()` opens the saved `/kiosk` URL with `HttpURLConnection`, leaves its default redirect-following behavior enabled, and treats any final HTTP status from 200 through 399 as reachable. The admin console's `refreshServerStatus()` and URL-change `validateAndSaveUrl()` make similar requests: they follow redirects by default and accept any 200–399 response as reachable or verified. Android documents that `HttpURLConnection` follows redirects by default. The kiosk WebView separately blocks a redirect outside the approved origin/path and reports a non-retryable policy failure. A server or proxy that redirects the kiosk route can therefore make a native probe contact a different destination, report success even though the visitor page cannot load, and in the URL-change flow save the original endpoint before the WebView rejects its redirect. The health probe also requests the full kiosk page instead of a small health resource.

**Fix:** disable redirect following for all three probes and require the exact expected status from the approved endpoint. Prefer a dedicated lightweight health endpoint whose response is checked without following redirects; verify the effective URL remains on the approved HTTPS origin. Keep redirect behavior covered by WebView/probe integration cases for same-origin allowed paths, same-origin blocked paths, and off-origin targets. [Android `HttpURLConnection` reference](https://developer.android.com/reference/java/net/HttpURLConnection.html)

### Low: Android classifies captive-portal connectivity as a kiosk-server outage

When the server probe fails, `MainActivity.networkIsConnected()` treats `NET_CAPABILITY_INTERNET` alone as proof that the tablet has usable connectivity, and `ConnectivityFailureRules.failure()` consequently displays “Reconnecting to Elite RF” / “service temporarily unavailable.” Android documents that a captive-portal network can have `NET_CAPABILITY_INTERNET` while lacking `NET_CAPABILITY_VALIDATED`; the current classifier therefore reports the kiosk server as the problem when the network still requires sign-in or cannot reach the general internet. This does not change the server probe result, but can send reception or IT to investigate the wrong component.

**Fix:** distinguish network transport, captive-portal state, Android's validated-connectivity signal, and the actual approved kiosk-endpoint probe. Show a network sign-in/connection message when the portal is detected or the network is unvalidated, while retaining the endpoint probe as the authority for kiosk availability. Add controlled tests for offline, captive portal, validated network with kiosk down, and reachable private kiosk endpoint. [Android `NetworkCapabilities` reference](https://developer.android.com/reference/android/net/NetworkCapabilities)

### Medium: photo validation checks only the JPEG start marker

The backend decodes base64, checks the first two bytes for JPEG SOI, and enforces a byte limit, but does not fully decode the image, enforce pixel dimensions, or strip metadata before saving it. A malformed or highly expanded image can fail later in admin viewers, and metadata can persist longer than intended.

**Fix:** decode with a maintained image library in a resource-bounded worker, enforce format/dimension/pixel limits, re-encode to the approved JPEG size/quality, strip EXIF and other metadata, and reject failures before recording the visit. Add malformed and oversized-dimension cases to tests.

### Low to medium: visitor text accepts control and bidirectional formatting characters

`create_checkin()` applies length and basic email checks but does not reject control or Unicode format characters in names, company, phone, or email. These values are later shown in the admin table, CSV, and email; HTML escaping prevents markup injection but does not stop bidirectional overrides or invisible control characters from making visitor identity or contact text misleading. The PDF export strips Unicode `Cc` and `Cf` characters, so the same record can also appear differently across export formats.

**Fix:** validate visitor and employee text against an explicit character policy that rejects unsafe control and bidirectional formatting characters while preserving legitimate international names. ### Low to medium: PDF export font cannot represent all accepted visitor scripts

`build_visits_pdf()` registers ReportLab's bundled `Vera.ttf` and uses it for visitor values, but the current workspace's bundled font character map has no glyph entries for common Cyrillic and CJK characters (for example U+0416 and U+4E2D). Visitor fields accept those scripts and the PDF code preserves them, so those identities cannot be faithfully displayed in the PDF export even though the database and CSV retain the text. ### Low to medium: CSV formula guard is not universal across locales or Excel save/reopen

`safe_csv_cell()` prefixes ASCII `=`, `+`, `-`, and `@` markers, but it does not recognize full-width `＝`, `＋`, `－`, or `＠`; OWASP notes that some spreadsheet applications/locales may interpret these as formula starters. The current mitigation prepends an apostrophe to the original cell text. OWASP also warns that Excel may remove common CSV escaping when a file is saved and reopened, potentially reactivating a formula. Because visitor-controlled names and company values are included in the authenticated CSV export, a record could be interpreted as a formula in an affected locale or after an unsafe spreadsheet round trip. Confirm that the mitigation does not corrupt downstream imports.

### Medium: email delivery has unavoidable duplicate risk after an ambiguous Graph response

The notification worker retries pending failures. If Microsoft Graph accepts a message but the response is lost before the kiosk records `sent`, the retry can send the same notification again. The local check-in submit lock does not cover this failure mode.

**Fix:** explicitly document delivery as at-least-once unless a deduplication mechanism is implemented. Persist a stable notification operation ID and reconcile ambiguous outcomes against the sender mailbox or a durable send ledger before retrying. Alert an administrator when the result cannot be resolved rather than silently promising exactly-once delivery.

### Low: visitor alert timestamps omit their UTC timezone

SQLite's `CURRENT_TIMESTAMP` default stores UTC text in `YYYY-MM-DD HH:MM:SS` form without a zone suffix. `email_message()` places the raw `created_at` value after “Checked in:” without adding “UTC” or converting it, while its fallback string does include “UTC”. Recipients can read the normal value as local time; the discrepancy can be several hours. The admin table correctly appends `Z` before parsing and converts to America/Chicago, and the PDF export labels the field UTC, so the email is inconsistent with both displays. **Fix:** format the alert timestamp consistently as an explicitly labeled timezone, such as converting UTC to America/Chicago and showing CST/CDT, or appending “UTC” to the stored UTC value. Apply the same formatter to normal and fallback timestamps, and cover standard and daylight-saving dates in the notification formatting tests.

### Medium: full-history exports grow without a bound

The visit table is retained without an age limit, while CSV/PDF export loads the full history into memory and the PDF builder constructs the complete document synchronously. In addition, every `/api/admin/health` request runs `SELECT COUNT(*) FROM visits`; the open dashboard polls this endpoint every 15 seconds. That count scans the growing visits table repeatedly while check-ins and other database writes share the same SQLite file. Long-term growth can therefore make exports slow or memory intensive and add recurring database load during normal dashboard use, particularly if visitor volume increases.

**Fix:** define an approved retention/archive policy. If indefinite retention is required, stream or paginate exports, impose an explicit export size/time limit, and test realistic multi-year data volumes; keep large exports off the request thread. Avoid rescanning the full visits table on each dashboard poll by using a safely maintained or cached count, or by refreshing it less often; preserve clear staleness semantics for that total.

### Medium: Python dependency ranges permit unreviewed version drift

`requirements.txt` specifies open version ranges for MSAL, cryptography, and ReportLab without a lock file or package hashes. Clean installs can resolve different dependency versions over time, reducing reproducibility and making it harder to tie a tested build to a reviewed dependency set. Updates are also not reliably applied by rerunning setup: the Debian installer reuses its existing virtual environment and runs `pip install --requirement` without `--upgrade`, so an installed version that still satisfies the range can remain unchanged; the Windows setup script runs the install only when required imports are missing. A reinstall can therefore leave the running service on an older allowed dependency even when a newer approved version is available.

The MSAL lower bound is `1.31.0`, which permits versions before `1.36.0`. In MSAL `1.35.1`, the authorization-code flow builds its PKCE code verifier with `random.sample()`; the app passes its own state generated by Python `secrets`, but MSAL also creates the PKCE verifier and OIDC nonce. MSAL's `1.36.0` release changed PKCE, state, and nonce generation to the cryptographically secure `secrets` generator. If an older allowed version is resolved from a cache or package mirror, the OAuth flow therefore uses a non-cryptographic PRNG for values that protect code interception and OIDC replay. The exact production-resolved MSAL version is not available. [MSAL 1.35.1 auth-code-flow source](https://github.com/AzureAD/microsoft-authentication-library-for-python/blob/1.35.1/msal/oauth2cli/oauth2.py), [MSAL PR #894](https://github.com/AzureAD/microsoft-authentication-library-for-python/pull/894).

**Fix:** require MSAL `1.36.0` or newer, then produce a reviewed lock/constraints file with exact versions and hashes, build from it in a controlled pipeline, record an SBOM, and schedule dependency vulnerability updates with a deliberate rebuild and regression review. Make deployment install the exact locked environment for that release (preferably in a fresh versioned virtual environment) rather than assuming a repeated requirements install updates already-satisfied packages. Add dependency-policy checks that fail if an older MSAL release or a known-vulnerable cryptography build enters the production lock.

### Medium: administrator access is a single shared password with no second factor or per-person identity

The backend supports one owner password, and successful sessions are valid for 12 hours. There is no individual admin account, MFA, role separation, or idle timeout. A compromised/shared password can expose all visitor records and photos; the current audit table cannot identify which administrator performed most actions.

**Fix:** use company SSO with MFA and per-person accounts/roles where available. Until then, restrict admin routes to the managed admin network, issue a strong unique owner credential through an approved secret manager, shorten the session lifetime and add idle expiry, and log security-relevant admin events without visitor PII.

### Medium if untrusted same-site origins exist: a simple form can disrupt Microsoft 365 alerts

`POST /api/admin/notifications/disconnect` and `/api/admin/notifications/certificate/generate` both check the admin cookie but do not parse a request body, require JSON, validate `Origin`/`Sec-Fetch-Site`, or require a CSRF token. A browser form on an untrusted sibling subdomain can send these simple POSTs to the kiosk; `SameSite=Strict` does not make sibling subdomains cross-site under cookie site semantics, even though they are different origins. Disconnect removes the delegated token cache and stops visitor email alerts. Certificate generation replaces the saved certificate and then disconnects the account, also interrupting alerts until the new certificate is registered with Entra and the account is reconnected. `GET /api/admin/notifications/connect` also creates an OAuth flow and should not be a state-changing GET. `POST /api/admin/logout` has no origin check and can be induced from a sibling site to clear the admin cookie, causing a forced logout. [IETF cookie same-site definition](https://datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis/).

**Fix:** require a CSRF token and exact same-origin validation for every cookie-authenticated state-changing request, including disconnect and OAuth initiation; require `Sec-Fetch-Site: same-origin` where supported. Convert the connect endpoint to POST. Keep OAuth callback state/nonce validation as its separate protocol check, and test a cross-origin sibling form POST with a valid admin cookie.

### Low to medium if Debian proxy settings drift: the admin session cookie can lose `Secure` without a startup warning

`session_cookie()` adds the `Secure` attribute only when backend TLS, `KIOSK_EXTERNAL_HTTPS`, or `config.cookie_secure` is enabled. The Debian environment reconciler forces `KIOSK_EXTERNAL_HTTPS=true` when the installer runs, but `run.py` does not require external HTTPS for the loopback Apache deployment and `warn_on_unsafe_configuration()` only reports a missing secure-cookie setting when the backend binds to a non-loopback address. If HTTP is also reachable for the host, the cookie can then be sent over that unencrypted path. This is conditional on post-install configuration drift, not the value produced by the current Debian installer.

**Fix:** add an explicit trusted-proxy deployment mode that requires `KIOSK_EXTERNAL_HTTPS=true` and fails readiness or startup when disabled for the Debian service. Keep `Secure` enabled for both setting and clearing admin session cookies in that mode, and verify the effective `Set-Cookie` header through the deployed Apache vhost after every environment-file change.

### High if deployment secrets are incomplete: a known placeholder session-signing key is accepted

The release builder seeds `config.json` with the literal session secret `replace-this-with-a-long-random-secret`. Production startup warns about a few exact placeholder strings but does not recognize this one or require a minimum secret length. If an operator configures `KIOSK_ADMIN_PASSWORD_HASH` but omits `KIOSK_SESSION_SECRET`, the environment password disables first-run setup while the known config placeholder remains the HMAC signing key. The Debian environment reconciler also preserves any nonempty value other than one exact placeholder without checking length or entropy; its test explicitly preserves `synthetic-preserved-secret`, so a short or guessable value can remain the active HMAC key. The Debian guide calls the preserved value random, but the helper does not verify that. An attacker who knows or guesses the key can forge an administrator session cookie.

**Fix:** fail closed in production unless the effective session secret is cryptographically random, sufficiently long, and not any known release placeholder, regardless of which password source is configured. Make both Windows and Debian setup helpers validate the effective secret, regenerate or reject weak values before enabling the service, and add startup coverage for env-password/missing-secret, short-secret, and predictable-secret cases.

### Low if kiosk.env contains duplicate controlled keys: Debian reconciliation can rotate the effective session secret unexpectedly

The reconciler then removes every duplicate and writes back only that first value. Add a fixture with duplicate session-secret assignments and verify reconciliation cannot silently change the value systemd would use.

### Medium: administrator actions are not attributable

The live visit-deletion route writes a database audit event, but the `Database.void_visit()` helper that records voids has no caller; the active `PATCH /api/admin/visits/{id}` route writes status through `update_visit_status()` without an audit event. Add privacy-filtered request/error logging with controlled retention, and make sure expected production service managers persist and alert on those logs. For Windows tasks, redirect sanitized supervisor and backup output to a protected, rotating log or Windows Event Log and alert on repeated child restarts or failed backups independently of Task Scheduler's task-object status. Protect and retain both audit and operational trails under company policy.

### Low if reception must track how each visit ended: visitor-status updates exist only in the backend

`PATCH /api/admin/visits/{id}` accepts `waiting`, `met`, or `cancelled`, and the database stores the value, but `buildVisitRow()` displays neither the current status nor a control to change it. ### Medium: the Android recovery code remains valid after use

`PinAuth.verifyRecovery` checks the saved recovery hash and returns success without consuming or rotating the code. A code intended to be shown only once therefore remains a reusable administrator credential indefinitely if copied or photographed. Failed recovery-code guesses also do not increment the persisted `failed` counter or trigger `locked_until`; only a lockout already caused by PIN failures is honored. The 24-character code uses a 32-symbol alphabet (120 bits of generated entropy), so this is not a practical guessing path, but it leaves recovery verification without the PIN path's abuse throttling and can permit repeated expensive PBKDF2 checks from the physical setup/admin flow.

**Fix:** make recovery codes single-use; after successful recovery, invalidate the used hash and require a new PIN plus a newly displayed recovery code, or require the PIN immediately and rotate the recovery code. Apply a persisted rate limit to failed recovery attempts as well as PIN attempts, with tests for recovery-code replay, repeated failures, and lockout across app/process restart.

### Medium: malformed Android PIN state is treated as configured and can lock out administrators

`PinAuth.configured()` only checks that the `pin_hash` and `recovery_hash` preference keys exist; it does not validate either encoded hash or the corresponding salts. `MainActivity.onCreate()` therefore skips secure setup when those values are present but truncated or malformed. Corrupt hash encodings become empty arrays and all checks fail; a malformed Base64 salt is decoded without error handling in `salt()` and can throw during PIN/recovery verification on the UI thread. A missing or valid-but-wrong-length salt instead makes credentials fail to match. The normal kiosk can continue running, but there is no in-app administrator recovery path for this state. Credential writes also update each salt separately from the hashes that depend on it, so an interrupted credential update can leave mismatched material.

**Fix:** validate all four stored values and expected lengths before reporting the PIN gate configured, and make malformed-state verification fail safely without crashing. Write each salt and its dependent hash through one `SharedPreferences.Editor` transaction. Provide a controlled, documented repair path that requires the approved physical/device-owner recovery procedure; never silently replace credentials when validation fails. Exercise missing, malformed, wrong-length, and interrupted-update states in tests against production `PinAuth`.

### Low: the recovery-code field is ignored while a failed PIN remains entered

`verifyAdministrator()` always checks a nonblank PIN field before the recovery field. After an incorrect PIN, the UI leaves that value in place, so entering a recovery code in the field labeled “Or enter recovery code” still retries the failed PIN and does not attempt recovery until the user manually clears the PIN field.

**Fix:** clear the PIN field after a failed attempt or make the two credential inputs mutually exclusive with a visible selector. Add an interaction test for wrong PIN followed by recovery-code entry without requiring the user to discover that the other field must be cleared.

### Low: failed recovery-code attempts bypass the persisted administrator lockout counter

`PinAuth.verifyPin()` increments the shared `failed` counter and establishes `locked_until` after five failures, but `PinAuth.verifyRecovery()` does not increment the counter when a code is wrong. A person at the tablet can therefore submit unlimited recovery-code guesses without triggering the five-failure lockout. A successful recovery does reset `failed`, but it does not invalidate the code; code reuse is tracked separately above. The 24-character recovery code has high entropy, so this does not by itself make authentication guessable; it does leave failed recovery attempts outside the documented throttling behavior and enables repeated expensive KDF work.

**Fix:** route both credential checks through one persisted, atomic failure/lockout state: count failed recovery attempts and refuse expensive hashing while locked. Keep separate counters only if the policy intentionally specifies that, and document the distinction. Add production-`PinAuth` tests for wrong PIN/recovery sequences, success reset behavior, lockout across process recreation, and five recovery failures.

### Low to medium: Android PIN and recovery input is hashed without a length bound on the UI thread

`showAdminGate()` passes the full contents of both `EditText` fields into `PinAuth.verifyPin()` or `verifyRecovery()`. Those methods call PBKDF2 synchronously through `PinAuthCore.matches()` without first requiring the PIN's documented maximum length or the recovery code's fixed format. A physically present user who pastes an unusually large value can make the main UI allocate and hash that entire input, stalling kiosk/admin interaction before the failure counter can help.

**Fix:** validate PIN length and recovery-code length/alphabet before deriving a hash, enforce the same limits in the `EditText` filters and `PinAuth` core, and run the KDF off the UI thread if the device timing warrants it. Count malformed attempts under the same lockout policy and test oversized input responsiveness.

### Low to medium: the citizenship response is collected in the form but discarded by the backend

The kiosk HTML requires a U.S.-citizenship response, but the current database schema has no corresponding field and `create_checkin` does not save it. ### Medium: concurrent settings/password writes share one temporary filename

`save_config` writes every configuration update to the fixed sibling path `config.json.tmp` and then replaces `config.json`. The HTTP server is threaded, and password changes, notification settings, and first-run setup can write configuration concurrently. Concurrent writers can truncate/interleave the same temporary file or cause one replace to fail, risking a failed admin operation or malformed/lost configuration. The file is also not flushed/fsynced before replacement, so a power loss can lose a successful settings update. The encrypted Microsoft 365 setup and token-cache writers use unique temporary files and fsync their contents, but omit a parent-directory sync after `os.replace`, leaving a narrow post-success power-loss gap for a newly saved mailbox connection or refreshed token cache. The Debian environment-file replacement has a separate finding below. [Python file flushing and `fsync`](https://docs.python.org/3.11/library/os.html#os.fsync), [Linux `fsync(2)` durability notes](https://man7.org/linux/man-pages/man2/fsync.2.html).

**Fix:** serialize configuration reads/modify/writes under one process-wide lock and give each save a unique temporary file in the same directory before atomic replacement. Add concurrent-writer coverage and verify the final settings survive reload/restart.

### Low if power is lost immediately after a successful save: settings file replacements may not be durable

`save_config` does not flush/fsync its temporary file before replacement. The encrypted Microsoft 365 settings and token-cache writers fsync their temporary file contents but do not sync the parent directory after `os.replace`. A sudden power loss after the API reports success can therefore lose the acknowledged configuration update, mailbox connection, or refreshed token cache. This is a crash-consistency risk; it was not reproduced. Debian `kiosk.env` has a separate, already-listed directory-sync issue. [Python `os.fsync`](https://docs.python.org/3.11/library/os.html#os.fsync), [Linux `fsync(2)` directory durability](https://man7.org/linux/man-pages/man2/fsync.2.html).

**Fix:** flush and fsync each temporary file before replacement; on POSIX, fsync the parent directory after replacement and before reporting success. Define corresponding Windows durability behavior. Add fault-injection coverage around file fsync, replace, directory fsync, and restart for config and encrypted Microsoft 365 state.

### Low if the Debian VM loses power during installation or upgrade: reconciled kiosk.env replacement is not directory-synced

`configure_kiosk_env.reconcile_environment()` flushes and fsyncs its temporary file, changes its ownership and mode, then atomically replaces `/etc/elite-rf-visitor-kiosk/kiosk.env` without syncing the parent directory. `install_debian.sh` continues to enable/start the service and report success after the reconciler returns. On POSIX filesystems, syncing the file contents alone does not guarantee that the directory-entry replacement survives a sudden power loss; the prior environment may reappear or the rename may be lost, potentially losing the enforced external-HTTPS/setup/backup flags or newly generated session secret. This requires a crash before the parent-directory update is durable; it was not reproduced. [Python `os.fsync`](https://docs.python.org/3.11/library/os.html#os.fsync), [Linux `fsync(2)` directory durability](https://man7.org/linux/man-pages/man2/fsync.2.html).

**Fix:** after `os.replace(temporary, path)`, open and fsync `path.parent` on POSIX, and fail the installer if the required durability step fails. Add fault-injection coverage around file fsync, replace, and directory fsync, then verify after restart that the enforced flags and effective session secret match the acknowledged setup state.

### Medium: concurrent Microsoft 365 setup operations can overwrite a newer certificate or app configuration

The setup, certificate-generation, and certificate-upload routes each load the encrypted Microsoft 365 settings, modify a copy, and atomically replace the settings file, but they do not serialize that read-modify-write sequence. `ThreadingHTTPServer` handles requests concurrently, and the dashboard disables only the button for the operation already running; setup, generation, and upload controls can still start overlapping requests, as can separate administrator tabs. If one operation saves after another, its stale settings copy can restore an older certificate/key or drop a newly generated/uploaded certificate. The public certificate download can then disagree with the private key used by notification delivery, or saved tenant/client/redirect values can revert. Unique temporary filenames prevent partial-file collisions but do not prevent this lost-update race. `save_settings()` fsyncs the temporary file before replacement but does not sync the parent directory on POSIX, so a sudden power loss can also lose the new settings entry after the route reports success. No concurrent Microsoft 365 settings test was found.

**Fix:** serialize the full load-validate-update-save-disconnect sequence with a shared application lock, re-read settings only after acquiring it, and make the dashboard disable all related setup/certificate controls while one operation is pending. ### Medium: interrupted check-ins can leave unlinked visitor photos that backups retain

Check-in writes a hidden temporary photo and renames it to its final `.jpg` name before inserting the visitor row. A power loss or process termination between those steps bypasses the exception cleanup and leaves a photo with no database record. This can happen during an expected service stop as well as a crash: `run.py` has no `SIGTERM` handling or request-drain protocol, the Debian systemd unit defines no stop command/override, and the Windows stop helper force-stops Python while the launcher kills its child during cleanup. systemd's default stop signal is `SIGTERM`; this unit does not override it or provide an application-level drain. [systemd stop and signal behavior](https://www.freedesktop.org/software/systemd/man/latest/systemd.kill.html). An active check-in can therefore be terminated during maintenance or upgrade without the application removing the staged/final photo or reporting whether its database commit completed. Even when an insert error is caught, the handler releases `storage_operation_lock` before deleting the staged/final photo in its exception block; a concurrent backup can acquire the lock in that gap and archive a photo whose database transaction failed. Startup cleanup only processes queued deletions. Backup creation archives every regular file under `storage/photos`, including unreferenced JPEGs and leftover `.tmp` files; backup verification checks that each database photo has a file, but does not reject extra photo files. These abandoned photos can accumulate outside visitor retention/deletion workflows and be copied into backups.

**Fix:** keep exception cleanup under `storage_operation_lock`, add locked startup reconciliation between the photo directory and database references, and make backup creation include only files referenced by its consistent database snapshot. Quarantine or remove only confirmed unreferenced files after a safe recovery policy, and alert rather than silently deleting when the database is unhealthy. Make backup verification reject unexpected files and add crash-boundary plus failed-insert/backup-race coverage for both temporary and renamed photo stages.

### Medium if backup archives can be untrusted or unexpectedly large: verification can exhaust memory or disk

`verify_backup()` decompresses every ZIP member with `testzip()` and reads the entire SQLite database member into memory with `archive.read()` before writing it to a temporary file. The verifier sets no compressed-size, uncompressed-size, file-count, or database-size limit, and the Debian restore CLI checks free staging space only after verification has already decompressed the archive. It also accepts ZIP directory entries under `storage/photos/` as manifest inventory members, while `_validate_archive_layout()` treats every allowed entry as a file; apply mode later tries to open a directory as a new file in the pre-created photo directory and fails during staging. Thus a malformed archive can pass verify-only validation but fail when applied. A crafted or unexpectedly large archive can also consume excessive CPU, memory, or temporary storage during verification; apply mode invokes the same verifier as root.

**Fix:** validate the complete restore layout before accepting an archive: allow only regular files at the exact supported paths, reject directory/special entries, and require verify-only and apply modes to use the same validated member list. Check compressed size, entry count, per-file and total uncompressed size, and available temporary space before decompression. Stream members to bounded temporary files rather than loading the database into memory, and reject layout or limit violations with a clear error. Set limits from measured production backup sizes with documented headroom.

### Medium if restoring across application versions: a valid newer SQLite schema can be installed into an older app

`verify_backup()` checks SQLite `quick_check`, foreign keys, and photo references, but does not read or compare `PRAGMA user_version` with the application's `SCHEMA_VERSION`. It also writes `format_version` into new recovery manifests but never validates the manifest's version when verifying an archive. The restore tool can therefore accept and apply a structurally valid database from a newer release, or a manifest that declares a future format whose current file list and photo-count fields happen to pass. On startup, `Database.initialize()` explicitly refuses a database whose schema version is newer than the running app supports, so a rollback or mismatched restore can replace live state successfully and then leave the service unable to start; unknown manifest semantics are likewise detected too late, if at all. The previous runtime tree is retained for manual rollback, but the compatibility failure can be detected only after the swap.

**Fix:** have backup verification require a supported `format_version` and report the database schema version; make both verify-only and apply modes reject future format or schema versions before touching runtime paths. Record the app and schema versions in backup metadata and test unsupported manifest/database versions through the verifier and both restore modes.

### Medium if rollback itself encounters a filesystem error: an incomplete restore can lose its blocking marker

`restore_backup()` removes `.restore-in-progress` after swapping the live paths, then syncs the runtime directory. If that sync fails, the exception path attempts to recreate the marker but suppresses any error from `write_text()`, `chmod()`, or the second directory sync. If rollback also fails, the function reports that recovery is incomplete and preserves the rollback directory, but the marker may be absent. A later restore invocation checks only for the marker and could proceed against the partially restored tree instead of refusing until an operator reconciles the preserved rollback state. This requires a filesystem error during marker durability plus an unsuccessful rollback; no such failure was reproduced.

**Fix:** make restore state durable before every live-path mutation and never silently suppress failure to persist an incomplete-state record. If recovery metadata cannot be durably restored, fail closed through a separate recognizable journal/rollback-state check and require explicit operator reconciliation before another apply. Add failure-injection coverage for marker unlink, directory sync, marker recreation, and rollback rename failures, and verify a subsequent apply is refused whenever the prior restore is unresolved.

### Low if the restore guard is replaced by a dangling symlink: systemd can start during unresolved restore state

Both Debian systemd units use `ExecStartPre=/usr/bin/test ! -e .../.restore-in-progress`. On Linux, `test -e` is false for a dangling symlink, so the negated test succeeds and permits the service or backup job to start. `restore_backup.py` explicitly rejects the same marker path when `is_symlink()` is true, leaving the startup guard weaker than the restore tool's own check. **Fix:** have the unit preflight reject both existing targets and symlinks, including dangling symlinks (for example, check `! -e` and `! -L`), or call one shared root-owned validation helper. ### Low if policy requires forensic erasure: deleted visitor rows may remain in SQLite WAL history

Each application database connection enables `PRAGMA secure_delete = ON`, which overwrites deleted content in database pages, but connections also use persistent WAL mode. WAL records database-page versions and can retain earlier frames until the WAL is checkpointed and reset; SQLite says a reset can be held up by an open reader. **Fix:** define in the approved retention policy whether dashboard deletion means logical removal from the live application or forensic erasure from live storage and retained copies. If stronger erasure is required, design and validate an encryption/key-destruction approach that covers the database, WAL, photos, exports, and backups; a checkpoint request alone is not a complete erasure guarantee.

### Medium if using Windows maintenance stop or a shared host: the stop helper is broad and the supervisor restarts the backend

`tools/stop_backend.ps1` force-stops every `python.exe` process whose command line contains `run.py`, without checking that the script is this project's `run.py` or that it is listening on the kiosk port. On a shared workstation, this can terminate unrelated Python applications and interrupt their work. In the supported Windows deployment, the scheduled task runs `tools/supervise.py`, which waits for the backend child and restarts it five seconds after any nonzero exit. Killing only the `run.py` child therefore leaves the supervisor alive and the kiosk returns shortly after the helper prints “stop requested”; this does not create a reliable maintenance window and forced termination skips graceful database/request shutdown.

**Fix:** give the supervisor an explicit graceful-stop mechanism that stops new requests, drains active work, and exits without restarting its child. Have the helper target only this project's named scheduled task/supervisor, prevent the task from restarting during the requested maintenance window, and verify both the supervisor/task and kiosk listener are stopped before reporting success. Add a Windows test where the supervisor owns a child, the stop operation is requested, and no replacement backend starts; retain a separate test that an unrelated Python process is untouched.

### Medium if using dashboard-managed Microsoft 365 on Windows: setup readiness requires the legacy app-only environment

`tools/company_setup.ps1` marks Microsoft 365 ready only when `M365_TENANT_ID`, `M365_CLIENT_ID`, `M365_SENDER_ADDRESS`, certificate paths, and thumbprint are present in `.env`. The current Microsoft 365 guide instead documents the dashboard-managed delegated mailbox flow, whose setup is stored encrypted under runtime `data/` and does not require those `M365_*` variables. The backend permits that flow over direct trusted HTTPS, but the Windows setup script still blocks final readiness unless the legacy app-only configuration is also populated. This can force unnecessary app-only credentials/private-key distribution or prevent an otherwise configured delegated mailbox from passing the documented company setup.

**Fix:** make the Windows readiness check recognize a connected, ready dashboard-managed account, or explicitly label the checker as legacy app-only and provide a separate supported delegated-flow acceptance path. Keep the launch gate requiring a controlled end-to-end test email, independent of which provider flow is selected.

### High: a tablet reboot can remove the maintenance auto-relock

`MaintenanceController.enterMode` schedules an exact `RTC_WAKEUP` alarm and stores an absolute wall-clock deadline. Android clears scheduled alarms on reboot. On boot, `MaintenanceController.enforceDeadline` only checks the saved deadline; when it is still in the future, it returns `true` without scheduling a replacement. `BootReceiver` then skips `KioskPolicy.apply`, and the full-maintenance countdown only stops updating when its deadline passes; it does not relock the device. A reboot during the open maintenance window can therefore leave the device in relaxed maintenance after the intended deadline. The wall-clock deadline can also be extended if the clock is moved backward while settings are available.

**Fix:** make boot recovery fail closed: either always end maintenance and reapply the locked policy on any reboot, or safely reconstruct and verify the remaining window, reschedule the alarm, and enforce the deadline from a reliable clock. Add acceptance coverage for reboot and clock-change attempts during both technician and full maintenance. Android documents that alarms are cleared by reboot and must be rescheduled: [AlarmManager reference](https://developer.android.com/reference/android/app/AlarmManager).

### High: maintenance relock depends on a background activity launch

**Fix:** make the dedicated-device home/Lock Task configuration provide a supported relock path that does not depend on an unrestricted background activity start, or use a platform-supported and narrowly scoped launch mechanism for the exact supported Android version. ### High if Device Owner policy restoration fails when maintenance ends: the relock deadline is discarded before the kiosk policy is verified

`MaintenanceController.finish()` removes the persisted maintenance mode/deadline and cancels its exact alarm before calling `KioskPolicy.apply()`. It ignores the returned Boolean, and `MaintenanceReceiver` also proceeds without checking whether the policy was restored. `KioskPolicy.apply()` can report failure when its checked Device Owner operations fail; exceptions during its sequence can also leave only some restrictions reapplied. If this happens at maintenance timeout or on an administrator's manual exit, the tablet has no saved maintenance deadline or retry alarm, and no controlled recovery loop is guaranteed. Depending on which policy operation failed, Settings or other system controls may remain available after the approved maintenance window. This contradicts `development/android-kiosk/docs/SECURITY_MODEL.md`, which asserts "exact automatic policy restoration" without stating that failure can discard the relock deadline.

**Fix:** retain a durable relock-pending state until the complete intended policy is applied and read back successfully. If restoration is incomplete, keep or recreate a bounded retry/watchdog and keep visitor entry unavailable; report the device as not locked until verification passes. Add failure-injection coverage for each policy setter/readback and physical checks that a failed first relock attempt retries without losing the deadline. ### High if maintenance-state removal fails to persist: a canceled relock can reactivate full maintenance after reboot

`MaintenanceController.finish()` removes the saved maintenance mode/deadline with `SharedPreferences.Editor.commit()` but ignores its Boolean result, then cancels the exact relock alarm and applies the kiosk policy. Android documents that `commit()` returns `true` only when the new values were successfully written to persistent storage. If the removal is not persisted, the current process sees the in-memory cleared state and can return to kiosk, but the old full-maintenance mode and future deadline may remain on disk. After a reboot, `BootReceiver` treats that stale state as active, and `MainActivity.onCreate()` calls `relaxFullMaintenanceRestrictions()` again. Because the old alarm was canceled and boot recovery does not schedule a replacement, the device can resume with the full-maintenance restrictions relaxed and no automatic relock. The `enterMode()` rollback path also removes maintenance keys with unchecked `apply()`, so a failed entry can leave stale full-maintenance state for a later restart. Preference-write failure was not reproduced. [Android `SharedPreferences.Editor.commit()` reference](https://developer.android.com/reference/android/content/SharedPreferences.Editor#commit())

**Fix:** represent maintenance and relock as an explicit durable state machine. Do not cancel the alarm or report relock complete until the cleared/pending state is verified as persisted and kiosk restrictions are read back; if persistence is uncertain, boot must fail closed and never reapply relaxed maintenance without a newly authenticated entry and a valid alarm. Make entry rollback use the same checked durable transition. Add tests that force failed preference writes, recreate the process/device state, and confirm no stale full-maintenance mode can relax policy or lose its relock deadline.

### Medium if Windows machine or user environment variables conflict with `.env`: setup can validate different settings from runtime

`load_local_env()` uses `os.environ.setdefault()`, so an already-defined process variable takes precedence over the package-root `.env`. ### Medium: notification retries can race the first send and deliver duplicates

### Low to medium if an administrator deletes a visit to suppress an unsent alert: the queued notification can still be sent after the visit is deleted

`retry_pending_notifications()` fetches pending visit and employee data into memory, then sends from that snapshot without a claim or a final existence/status check. ### Medium: Microsoft Graph throttling retries ignore the server's `Retry-After` delay

`send_email()` classifies HTTP 429 as retryable but discards the response headers. `deliver_notification()` then schedules retries using a fixed exponential sequence starting at 60 seconds, regardless of the wait Microsoft Graph requested. If Graph specifies a longer delay, the kiosk retries too early, consumes more throttled requests, and may exhaust its eight-attempt limit while the service still asks it to wait. Microsoft's guidance says to wait for `Retry-After` when present and use exponential backoff when it is absent. [Microsoft Graph throttling guidance](https://learn.microsoft.com/en-us/graph/throttling).

**Fix:** carry a validated retry time from the HTTP error response through `send_email()` to the persisted `notification_next_attempt_at`. Respect the server delay within a documented upper bound; use the existing exponential backoff only when no usable header is present. Add tests for numeric and date-form `Retry-After`, malformed values, and retry-limit behavior after a long throttle window.

### Medium: an unbounded notification retry batch can delay photo cleanup and scheduled backups

`pending_notifications()` loads every due pending visit into memory with no batch limit. `retry_pending_notifications()` sends that snapshot sequentially, and the production background loop runs photo-deletion cleanup before retries but checks/creates backups only after the entire retry batch returns. Each Graph send has a 15-second HTTP timeout, while token acquisition occurs before that timed request; a large backlog or slow identity-provider calls can therefore hold the single maintenance thread for a long time. New requests for cleanup wait until the batch finishes, and a due backup can miss its scheduled check by the same duration. This is most likely during a Microsoft 365 outage or after service downtime when many retries become due together.

**Fix:** cap each retry pass to a bounded batch and put notification delivery on its own worker with explicit concurrency/backpressure limits. Keep photo cleanup and backup scheduling independent of notification latency, and record queue age/depth plus last successful backup time in health status. Add a synthetic backlog test that proves cleanup and a due backup still run within documented limits while sends time out or token acquisition stalls.

### Medium if photo deletion errors accumulate: the unbounded cleanup queue can hold the storage lock and delay kiosk work

If filesystem errors leave a large queue while administrators continue deleting old visits, cleanup can grow into repeated all-rows scans and long lock holds, delaying check-ins, backup work, email retries, or service startup. This is conditional on a sizable backlog and slow/erroring storage; no backlog performance test was run.

**Fix:** process a bounded number of queued deletions per pass and back off per item after persistent filesystem errors. Batch directory fsyncs after a bounded group of successful unlinks, while retaining a durable queue entry until each deletion is safely complete. Expose queue depth and oldest-item age in health status, and test a large synthetic backlog with repeated unlink/fsync failures to verify check-ins, notifications, and backup scheduling remain within documented latency limits.

### Medium: Microsoft identity token errors can permanently fail alerts even when the error is transient

Both `_delegated_access_token()` and `_access_token()` treat an MSAL result without an `access_token` as a generic `ValueError`; `send_email()` maps every `ValueError` to notification status `failed`, which is not retried. MSAL can return structured result dictionaries containing an `error` when silent refresh or application token acquisition fails, and `acquire_token_silent()` can also return no token. **Fix:** preserve and classify sanitized MSAL error codes separately from credential/consent errors. Schedule bounded retries for transient identity-service failures, and mark permanent authorization failures as reconnect/configuration-required without retrying every minute. Keep correlation IDs or safe error codes for IT diagnosis while excluding tokens and private response details. Add tests for transient result codes, no-token silent results, invalid grants, and certificate/tenant failures, and verify the persisted notification state and dashboard guidance for each.

### Low to medium: a saved but unusable delegated cache prevents the app-only fallback

Document and test the configured provider, unreadable-cache, expired/revoked-token, disconnect, and app-only fallback states.

### Medium if inactivation is intended to revoke alert access: check-in and retry alerts can still target inactive employees

### Low to medium: one administrator's password mistakes can lock out all admins behind a shared IP

`login()` keys its persistent five-failure lockout only by client IP. Multiple authorized administrators behind the same office NAT or proxy share that key, so one person's mistakes (or another office user deliberately entering wrong passwords) blocks everyone at that address for five minutes.

**Fix:** document the shared-IP behavior, add administrator identity and MFA, and use layered per-client throttling plus monitoring rather than a lockout that lets one person deny service to every admin on a shared egress address.

### Low if untrusted local processes can reach the backend: forwarded addresses choose throttle buckets

In Apache mode, the backend accepts the first `X-Forwarded-For` value whenever the TCP peer is any loopback address. The packaged Apache template removes an incoming client-supplied `X-Forwarded-For` before proxying and appends the actual client address, which is the intended trust boundary. A different process running on the same host can connect directly to the loopback backend and choose arbitrary valid addresses to evade or deliberately distribute the per-address login throttle. This does not bypass the password check, but makes the throttle dependent on host isolation and correct proxy routing.

**Fix:** keep the backend reachable only through the managed proxy for normal clients, restrict untrusted local services/accounts from accessing its port, and validate the proxy's overwrite behavior in deployment acceptance. If local co-tenancy is expected, use a proxy/backend channel that authenticates the proxy rather than trusting every loopback peer.

### Low: malformed admin cookies can abort authentication without a controlled response

`admin_token()` passes the request's `Cookie` header to `http.cookies.SimpleCookie.load()` without catching `CookieError`. Python documents that parsing invalid cookie data may raise this exception and recommends catching it. Since `require_admin()` calls `admin_token()` before returning its normal 401, a malformed cookie on an admin-protected route can escape the handler, close that request without a JSON response, and emit an uncaught exception through the HTTP server's error path. The OAuth cookie parser already handles this exception, but the administrator parser does not. [Python `http.cookies` documentation](https://docs.python.org/3/library/http.cookies.html).

**Fix:** catch `cookies.CookieError` in the shared administrator-cookie parser and treat invalid input as a missing/invalid session so the route returns the normal 401. Add a request test with malformed cookie syntax for each shared authentication path and verify that no traceback escapes.

### Low: oversized decimal Content-Length can escape normal request error handling

`read_json()` and `read_urlencoded_form()` check that `Content-Length` contains decimal digits, then call `int(length_header)` before safely rejecting an excessively long value. Python 3.11's decimal integer conversion limit raises `ValueError` when the header has more digits than the configured limit. That exception is not converted to `RequestBodyError`, so an unauthenticated caller can trigger an unhandled handler exception rather than the normal 400/413 response on any endpoint using either parser. The headers are small enough to fit under common HTTP header-line limits. This is a malformed-input robustness issue; repeated parallel requests could add load to the uncapped threaded server. [Python 3.11 integer conversion limit](https://docs.python.org/3.11/library/stdtypes.html#integer-string-conversion-length-limitation).

**Fix:** reject an overlong decimal header before integer conversion (for example, compare digit count against the decimal representation of the maximum allowed body length), then catch conversion errors and return a controlled 400. Apply the same bounded parser to JSON and OAuth form bodies. Add tests with a synthetic Content-Length longer than Python's configured integer conversion limit and verify a controlled response without an uncaught traceback.

### Low: admin startup and login network failures have no visible recovery state

`loadAuthState()` is called on page load without a rejection handler. If the initial setup-state request fails, or the later session check fails, the page stays on the generic “Admin sign in” screen without telling the administrator that setup/session state could not be checked. `submitAuth()` likewise has no `try/catch` around the setup/login request; a rejected fetch produces no visible error or retry guidance, and an owner-password setup request whose response is lost may already have committed on the server. This can make first-run setup or sign-in appear unresponsive and leave operators unsure whether a retry is safe.

**Fix:** show a distinct loading/error state for auth discovery and a clear retry action when the request fails. Catch login/setup transport errors, preserve the entered password only as needed for an immediate retry, and explain that setup completion may need to be checked before retrying after an ambiguous response. Verify rejected requests, non-2xx responses, and a server-committed setup whose response is lost in browser-level coverage.

### Medium if login is reachable by a high-volume client: persistent throttle checks contend with visitor writes

Production `login()` calls `LoginThrottle.retry_after()` before reading the password. In persistent mode, `_persistent_retry_after()` opens a connection to the visitor database, starts `BEGIN IMMEDIATE`, and runs a stale-row `DELETE` on every login attempt before selecting the client's fingerprint. This acquires SQLite's writer reservation even for a normal unlocked login, and the `updated_at` cleanup predicate has no index. Each distinct client fingerprint can also create a separate row, and inactive rows are kept for 24 hours with no global row/size cap. A high-volume or distributed login flood can therefore serialize throttle checks, repeatedly scan and grow the throttle table, and contend with check-in, notification, and administrative writes in the same database; sustained traffic from many distinct addresses can consume storage as well as write capacity. Once the five-second busy timeout is hit, login can fail before returning its normal JSON response.

**Fix:** make the common lockout lookup read-only, move stale-row cleanup to a bounded periodic task or perform it only when needed, and index any cleanup predicate. Apply global connection and request limits at the proxy; cap or safely expire throttle records so hostile unique-client traffic cannot grow the visitor database without bound; and define a graceful busy-database response for login. Add a concurrency test that floods login checks from many unique client fingerprints while measuring bounded check-in write latency and throttle-table/storage growth.

### Medium if the admin login is reachable by an untrusted client: password inputs have no field-size limit before PBKDF2

The JSON parser allows bodies up to 7,000,000 bytes, the admin password field has no `maxlength`, and `verify_password` passes the entire submitted value to PBKDF2 before recording the failed attempt. `ThreadingHTTPServer` handles requests on separate threads, while each login checks the IP lockout before the expensive hash and records failure only afterward. A burst of concurrent guesses from one client can therefore test many passwords before any one of them trips the five-failure threshold; large password bodies also multiply the memory and CPU cost.

**Fix:** reserve/record authentication attempts atomically before hashing so concurrent requests cannot all pass the same precheck, enforce a small documented password byte/character limit in setup, change-password, and login paths, and bound concurrent expensive authentication work. Keep the Apache/admin-network access control as a separate required defense.

### Medium if the admin endpoints are reachable by untrusted clients: unauthenticated setup checks perform PBKDF2 before throttling

`GET /api/admin/setup-state` is unauthenticated and calls `owner_setup_required()`. With a config-managed owner password, that function runs `verify_password(DEFAULT_OWNER_PASSWORD, stored_hash)` on every request to determine whether first-run setup remains active. The public login handler performs the same PBKDF2 check before it asks `LoginThrottle` whether the client is locked out. Repeated setup-state requests therefore have no throttle at all, and locked login requests continue paying the KDF cost before receiving 429. Because the service uses `ThreadingHTTPServer`, concurrent requests can consume CPU and request threads without submitting a password or being stopped by the login lockout.

**Fix:** determine and cache first-run setup state during controlled startup and update it when the owner credential changes, or store an explicit setup-complete marker; do not derive setup state by hashing on every public request. Check the lockout before any password KDF and bound concurrent authentication work. Add tests proving repeated setup-state requests and locked login attempts do not invoke PBKDF2 after initial setup-state determination.

### High if a Windows or custom reverse-proxy deployment exposes first-run setup: the backend can mistake every proxied client for the local operator

`setup_allowed_for_client()` authorizes owner-password creation by checking whether the backend TCP peer is loopback. With a local reverse proxy, the backend sees the proxy's loopback connection for remote browser requests, so `/api/admin/setup` can be used by the first remote visitor to claim the owner account whenever no owner password exists. The Debian installer separately forces `KIOSK_DISABLE_REMOTE_OWNER_SETUP=true`, and the packaged Apache example restricts `/api/admin/` to an approved subnet, so this finding is conditional on a Windows/custom proxy path that does not preserve those protections. The Windows setup helper does not set the disable flag, and no proxy-side setup-path restriction is established for that topology.

**Fix:** disable web-based owner setup in every reverse-proxy deployment and configure the proxy to deny `/api/admin/setup` except from an explicitly approved setup workstation. Prefer binding first-run setup to a one-time host-generated secret or a local-only management channel rather than treating the proxy connection as the browser's origin. Add an integration test with a remote client reaching the backend through a loopback proxy and verify setup is denied after the approved provisioning window.

### Medium if `KIOSK_ADMIN_PASSWORD_HASH` is configured: invalid or excessive-cost hash can lock out admins or stall login

`owner_setup_required()` treats any nonempty `KIOSK_ADMIN_PASSWORD_HASH` as proof that the owner password is configured. `login()` then uses that value, while `verify_password()` returns false for malformed PBKDF2 strings. A typo, truncated environment value, or unsupported hash format therefore disables first-run setup and makes every login fail until an operator edits the host environment or config directly. The Windows setup helper has the same issue: `Test-OwnerConfigured()` returns true as soon as that variable is nonempty. The verifier accepts any positive integer iteration count in environment- or config-sourced hashes, with neither a minimum nor maximum bound, and computes the hash synchronously for each attempt. A very low count makes an exposed hash much cheaper to brute-force offline; an extreme count can make every login consume excessive CPU and tie up request threads.

**Fix:** validate the exact supported PBKDF2 hash format, salt/digest sizes, and a documented reasonable iteration range at startup and in readiness checks. Reject malformed or excessive-cost values with a clear host-side error while preserving a documented local recovery path; do not treat mere variable presence as a configured credential. Cover malformed, truncated, unsupported-format, below-range, and above-range hashes.

### Medium: the documented offline password reset can leave the active credential or existing sessions unchanged

The README recommends `tools/set_admin_password.py` for an offline reset. That helper updates only `config.json` and prints “Admin password updated.” The running server gives `KIOSK_ADMIN_PASSWORD_HASH` precedence over the config value, including when the variable is loaded from `.env`/`kiosk.env` at startup. In that deployment, the operator can complete the reset successfully while the old environment-managed password remains active. Alternatively, make the helper explicitly config-only, fail when an override is present, and document the protected password-and-session reset procedure. Add coverage for config-managed, process-environment-managed, and file-managed hashes plus pre-reset session invalidation.

### Medium: password change mishandles effective session-key rotation

### Low if the Bash provisioning script is used: Lock Task verification can fail on a valid device because `grep -q` closes the `adb` output pipe early

`provision_android.sh` enables `set -o pipefail`, then pipes the potentially large `adb shell dumpsys activity` and `dumpsys activity activities` outputs directly to `grep -Eq`. [Bash pipeline status](https://www.gnu.org/s/bash/manual/html_node/Pipelines.html), [GNU grep quiet-mode behavior](https://www.gnu.org/s/grep/manual/html_node/General-Output-Control.html)

**Fix:** capture each `dumpsys` result before matching it, or use a matcher that consumes the complete input while discarding output. ### Low if Android wall-clock time changes during a visitor session or PIN lockout: native cleanup and lockout durations become inaccurate

**Fix:** measure in-process inactivity with `SystemClock.elapsedRealtime()` (or another monotonic source), which Android recommends for interval timing and which continues during deep sleep. For a lockout that must survive process or device restart, use a design that detects inconsistency between persisted wall time, elapsed time, and reboot state, and fail closed on an implausible jump rather than trusting the adjusted wall clock alone. Keep wall-clock timestamps for schedules that must survive reboot. Inject clocks into the production idle and lockout paths; test simulated backward/forward corrections during visitor cleanup and PIN lockout, plus process restart and reboot behavior. ### Medium if restored archives are not fully trusted: restored config can redirect data paths or prevent startup

`verify_backup()` validates ZIP structure, CRCs, the recovery manifest, and SQLite integrity, but it does not validate the contents or schema of the archived `config.json`; the manifest is only an editable file list and has no signature or keyed authenticity check. `restore_backup.py` accepts that config, while production startup loads it and uses `database_path` and `photo_storage_path` directly in `root / value` without validating that they are the required relative paths or remain under the runtime root. Startup also assumes nested settings and numeric values have supported types: for example, a non-object `notification_settings` value fails when `.get("enabled")` is called, an invalid `automatic_backup_hours` value fails integer conversion, and malformed `employees` seed data can make SQLite initialization fail when the employees table is empty. `max_photo_bytes` is converted only when a visitor submits a photo, so a malformed value can break every photo check-in instead of failing startup. A string such as `cookie_secure: "false"` is truthy in Python and adds the `Secure` cookie attribute in a configuration intended for HTTP, which can cause admin sessions to fail on clients that do not treat the host as a secure context. A modified or substituted archive can therefore pass structural verification, redirect future visitor records/photos to another path writable by the kiosk service account, or leave the service unable to start or function after restore.

**Fix:** validate the full supported config schema, types, ranges, and fixed relative database/photo paths before a restore can replace live state and again before server startup. Require an object at the top level, a list of well-formed employee records, actual JSON booleans for flags, and bounded integers for photo and backup limits. Reject unknown or malformed structures, absolute paths, traversal, and values outside the allowed bounds; prove canonical path containment under the runtime root. Authenticate backup archives with a signature or MAC whose key is stored outside the archive and protected separately; keep access control and encryption as separate requirements. Add tampered-archive coverage for path redirection, malformed nested settings, bad employee rows, and invalid numeric/boolean values, and verify restore and startup reject them before live state changes.

### High if an untrusted user can modify the archive during privileged restore: validation and extraction use separate file opens

`restore_backup()` resolves the archive path, calls `verify_backup()` (which opens and closes it), calls `_validate_archive_layout()` in a second open, and later opens it again for extraction. `_validate_archive_layout()` accepts every member beginning with `storage/photos/` but does not itself reject `..` components; the ordinary traversal guard is only in the earlier verifier. If an untrusted user can replace a writable archive between those opens, the verifier can check one file version while the layout validator collects traversal names from a replacement and the extractor later reopens that path to write outside staging. This requires a race against a privileged restore and a replaceable archive path; an unchanged malicious archive is rejected by `verify_backup()`.

**Fix:** take a protected snapshot of the archive before validation and use that same immutable file or open file descriptor for verification, layout checks, and extraction. Make `_validate_archive_layout()` independently enforce canonical relative member names and reject `..`, absolute paths, backslashes, drive prefixes, links, special entries, and duplicate normalized names. Resolve and verify destination containment immediately before each staged write. Add a regression test that replaces the source archive between phases and proves apply cannot escape staging.
